## 一、项目速览

**SPZX（尚硅谷甄选）** 是一个基于 **RuoYi-Cloud v3.6.3** 改造的**分布式微服务电商平台**，覆盖了电商核心链路：

```
用户浏览商品(H5) → 加入购物车 → 提交订单 → 支付宝支付 → 扣减库存
                                     └→ 未支付 15 分钟自动取消(演示 1 分钟) → 解锁库存
```

同时保留了若依的**后台管理系统**（用户/角色/菜单/字典/日志/代码生成等）。

学习价值：这是一个"麻雀虽小五脏俱全"的微服务教学项目 —— 它把面试高频考点全部串起来了：

| 考点 | 本项目落点 |
|------|-----------|
| 微服务拆分/服务注册发现 | 13 个服务注册到 Nacos |
| 网关统一鉴权 | Gateway `AuthFilter` + JWT + Redis 会话 |
| 分布式缓存三兄弟 | 缓存穿透(bitmap)、击穿(分布式锁)、雪崩(随机过期时间) |
| 分布式锁 | Redis `setIfAbsent` + Lua 释放锁 |
| 消息队列可靠投递 | RabbitMQ 手动 ack + 确认回调 + 死信队列延迟消息 |
| 幂等设计 | Redis `setnx` 标记 + Lua 原子判断 |
| BFF 聚合层 | spzx-channel 用 CompletableFuture 并行聚合 |
| 分布式事务 | Seata + MQ 最终一致性（库存解锁/扣减走消息） |
| 接口安全 | `@InnerAuth` 内部调用校验、Feign 上下文透传 |

### 3.2 请求流转全景

```
浏览器/App
   │
   ▼
Nginx(80) ── /prod-api/* ──► Gateway(8080)
                               │ 过滤器链（按顺序）：
                               │  CacheRequestFilter（缓存请求体）
                               │  ValidateCodeFilter（/auth/login 验证码）
                               │  BlackListUrlFilter（URL 黑名单）
                               │  AuthFilter（JWT 鉴权 + Redis 会话，order=-200）
                               │  XssFilter（XSS 防护）
                               │  Sentinel（网关流控）
                               │  TraceIdFilter（链路追踪）
                               │
                               │  鉴权通过后注入请求头：x-user-id / x-username / x-user-key
                               │  并移除 from-source 头（防伪造内部调用）
                               ▼
                    ┌───────────┴────────────┐
                    │   路由 lb://服务名       │
                    │   /auth/** → spzx-auth  │
                    │   /product/** → spzx-product
                    │   /order/** → spzx-order
                    │   /channel/** → spzx-channel 等 13 条路由
                    └───────────┬────────────┘
                                ▼
             各业务服务 → MySQL / Redis / RabbitMQ / Seata / Sentinel
```

### 3.3 服务间调用关系（Feign 矩阵）

```
                    auth  system  product  user  order  channel  cart  payment
RemoteUserService      ✓                                              （spzx-system）
RemoteLogService       ✓
RemoteUserInfoService  ✓
RemoteFileService            ✓
RemoteCategoryService                          ✓  ← channel 调 product
RemoteBrandService                             ✓
RemoteProductService                           ✓   ✓(order)
RemoteUserAddressService  （auth 也调）          ✓  ← order 调 user
RemoteCartService                               ✓  ← order 调 cart
RemoteOrderInfoService                                        ✓  ← payment 调 order
```

**核心调用场景：**
- 后台登录：auth → system（查用户）→ system（写登录日志）
- H5 首页：channel → product（分类树 + 热销商品）
- 商品详情：channel → product（6 个接口并行聚合）
- 下单：order → cart（选中商品）+ product（价格/库存）+ user（收货地址）
- 支付：payment → order（查订单），支付成功经 MQ 通知 order，order 再经 MQ 通知 product 扣库存

## 四、学习路线（7 个阶段）

> 建议顺序：先"跑起来"建立全局观 → 再逐个模块精读 → 最后做优化练习。

### 阶段 0：前置知识自查（约 1 周）

- Java 21 基础 + Lambda/Stream（代码里大量使用）
- Spring Boot 3 基础（自动装配、@ConfigurationProperties、starter 机制）
- Spring Cloud 核心概念：注册中心、配置中心、网关、Feign、负载均衡
- MySQL 索引与事务、Redis 基础数据类型（String/Hash/Bitmap）
- 懂一点 RabbitMQ 基础概念（交换机/队列/路由键/死信）

> 自查方式：能独立解释"服务注册到 Nacos 后，网关怎么把请求转发给它"即可进入下一阶段。

### 阶段 1：先跑起来（1~2 天）

目标：本地启动 gateway + auth + system，完成一次"后台登录"。

1. 按[第八节](#八环境搭建与启动指南)准备基础设施（Nacos/MySQL/Redis/RabbitMQ）
2. 启动顺序：`spzx-system`（9201）→ `spzx-auth`（9200）→ `spzx-gateway`（8080）
3. 验证：
   - Nacos 控制台能看到 3 个服务注册
   - `curl http://localhost:8080/auth/login` 能拿到 token
4. 阅读 `seq.json`（登录时序图）对照代码走一遍登录

**里程碑**：理解了"网关 → 认证中心 → 系统服务 → Redis 会话"这条主链。

### 阶段 2：基础设施组件逐个吃透（1 周）

| 组件 | 读什么 | 问自己 |
|------|--------|--------|
| Nacos | 各服务 `bootstrap.yml`、`pom.xml` 属性 | 配置中心与注册中心各解决什么问题？`shared-configs` 是什么？ |
| Gateway | `AuthFilter`、`ValidateCodeFilter`、`GatewayConfig` | 为什么 JWT 校验放网关？`StripPrefix=1` 作用？白名单怎么配？ |
| Redis | `spzx-common-redis`、`RedisService`、`GuiguCacheAspect` | `@GuiguCache` 的 AOP 缓存原理？key 怎么生成？ |
| RabbitMQ | `spzx-common-rabbit`、`MqConst`、`OrderReceiver`、`ProductReceiver` | 手动 ack 为什么必要？延迟消息如何用死信队列实现？ |
| Sentinel | `spzx-gateway-dev.yml` 的 sentinel 段 | 网关流控规则怎么持久化到 Nacos？ |
| Seata | `spzx-common-seata` | 本项目实际用 Seata 吗？哪些链路用了"最终一致性"替代？ |

### 阶段 3：核心业务链路逐个攻破（2~3 周）

按依赖顺序学习，每个链路都要画**时序图 + 找代码验证**：

1. **认证链路**：`/login`（admin）与 `/h5/login`（会员）双端对照
2. **商品浏览**：channel 的 Index（首页）/ Item（详情）/ List（列表）/ Category / Brand
3. **购物车**：Redis Hash 结构、数量上限、价格刷新
4. **下单结算**：防重复提交 → 价格校验 → 库存锁定 → 落库 → 删购物车 → 延迟关单
5. **支付**：支付宝 WAP 下单 → 异步回调验签 → MQ 通知订单 → MQ 扣库存
6. **库存**：sku_stock 四字段模型、锁定/解锁/扣减三张 SQL

### 阶段 4：公共模块源码精读（1 周）

按依赖层次自底向上：

```
spzx-common-core      （地基：R/AjaxResult/JwtUtils/StringUtils/BaseController）
  └─ spzx-common-redis（RedisService + @GuiguCache 缓存切面）
  └─ spzx-common-security（HeaderInterceptor / PreAuthorizeAspect / InnerAuthAspect / TokenService）
  └─ spzx-common-rabbit（RabbitService + MqConst）
  └─ spzx-common-datasource / datascope / log / seata
```

**重点精读 `spzx-common-security`**，这是整个项目的安全内核：
- `HeaderInterceptor`：请求头 → `SecurityContextHolder`（Transmittable ThreadLocal，异步线程也能拿到）
- `TokenService`：创建/刷新/销毁令牌，Redis 会话 TTL 12h，剩余 <2h 自动续期
- `PreAuthorizeAspect`：`@RequiresPermissions` 权限校验 AOP
- `InnerAuthAspect`：`from-source: inner` 头校验
- `FeignRequestInterceptor`：Feign 调用时透传用户上下文

### 阶段 5：进阶主题（按需，可边面试边学）

1. **缓存三兄弟**：读 `ProductServiceImpl.getProductSku()` 的缓存 + 分布式锁 + 随机过期时间；`ItemServiceImpl.item()` 的 bitmap 缓存穿透防护；`updateProduct()` 的**延时双删**保证最终一致性
2. **分布式锁**：`checkAndLock` 的 `setnx` 幂等标记、`getProductSku` 的 Lua 释放锁 —— 思考：锁过期了怎么办？（引出 Redisson 看门狗）
3. **消息可靠性**：confirm 回调 + 手动 ack + 消费者幂等（`sku:unlock:{orderNo}` setnx 标记）
4. **BFF 聚合**：`ItemServiceImpl` 6 个 Feign 调用用 `CompletableFuture` + 自定义线程池并行
5. **接口幂等**：下单防重复提交的 Lua 脚本（`user:tradeNo:{userId}` 原子 GET+DEL）
6. **延迟队列**：`spzx.cancel.order` 交换机 + TTL + 死信队列实现延迟关单
7. **SkyWalking**：见 `doc/skywalking-全链路改造.md`

### 阶段 6：动手优化练习（检验学习成果）

代码里留下的"作业"和可优化点，先自己尝试，再对照[第九节](#九代码优化与待办清单)：

1. **库存一步到位**（ProductServiceImpl 注释中的作业）：
   把"检查库存 + 锁定库存"合并为一条 SQL：
   ```sql
   UPDATE sku_stock
   SET available_num = available_num - #{num},
       lock_num = lock_num + #{num}
   WHERE sku_id = #{skuId} AND available_num >= #{num}
   ```
   思考：为什么能合并？`for update` 行锁与乐观更新各自的适用场景？
2. **给 Redis 缓存加 Caffeine 本地缓存**（二级缓存）
3. **把 `getProductSku` 的分布式锁换成 Redisson**（解决锁过期问题）
4. **支付金额从写死的 `0.01` 改为订单真实金额**（AlipayServiceImpl）
5. **补一个单元测试**：库存锁定的并发场景

## 五、模块源码导读

### 5.1 spzx-gateway（网关，8080，WebFlux 响应式）

| 类 | 职责 |
|----|------|
| `filter/AuthFilter` | 核心鉴权：白名单 → 解析 JWT → 校验 Redis 会话 → 注入用户请求头 → 移除 from-source |
| `filter/ValidateCodeFilter` | /auth/login、/auth/register 的验证码校验 |
| `filter/CacheRequestFilter` | 缓存请求体（验证码过滤器需要读取 body，读后不可再读） |
| `filter/BlackListUrlFilter` | URL 黑名单 |
| `filter/XssFilter` | XSS 防护（转义请求参数） |
| `filter/TraceIdFilter` | 生成/透传 traceId（SkyWalking 用） |
| `handler/GatewayExceptionHandler` | 网关统一异常 → JSON |
| `service/ValidateCodeService` | 验证码生成与校验（Kaptcha） |

**阅读顺序建议**：AuthFilter（必读）→ ValidateCodeFilter（理解 body 缓存原因）→ 其余了解。

### 5.2 spzx-auth（认证中心，9200，无 DB）

|----|------|

### 5.5 spzx-user（会员服务，9206）

- `UserInfoController`：会员 CRUD（Feign 供 auth 登录用）

### 5.6 spzx-order（订单服务，9207）⭐核心

| 类 | 职责 |
|----|------|

### 5.7 spzx-channel（H5 BFF 聚合层，9208，无 DB）⭐亮点

| 类 | 职责 |
|----|------|
| `IndexController` / `IndexServiceImpl` | 首页：分类树 + 热销商品聚合 |
| `ItemController` / `ItemServiceImpl` | **商品详情**：6 个 Feign 调用 CompletableFuture 并行聚合 |
| `ListController` / `ListServiceImpl` | 商品列表/搜索 |
| `CategoryController` / `BrandController` | 分类/品牌 |
| `configure/ThreadPoolConfig` | 自定义线程池（聚合用） |

**设计意图**：给 H5 前端提供"一次请求拿全"的接口，屏蔽后端微服务拆分细节。

### 5.8 spzx-cart（购物车，9209，纯 Redis）

- Redis Hash 结构：大 key `user:cart:{userId}`，小 key `{skuId}`，value 是 `CartInfo` JSON
- 上限：50 个商品/购物车，单商品 99 件
- 加购时 Feign 调 product 拿 SKU 信息；列表页远程拉最新价格对比提示
- `@InnerAuth` 接口：`getCartCheckedList` / `updateCartPrice` / `deleteCartCheckedList`（供 order 调用）

### 5.9 spzx-payment（支付服务，9210）

- `AlipayServiceImpl`：生成支付宝 WAP 支付表单（注意 `total_amount` 目前写死 0.01，教学演示用）
- `PaymentInfoServiceImpl`：保存支付记录 → 回调时更新状态 → MQ 通知订单
- `AlipayController`：`submitAlipay`（下单支付）、`callback/notify`（异步回调，验签）
- `PaymentReceiver`：监听支付相关消息

### 5.10 spzx-api（Feign 接口层）

每个 API 模块 = 1 个 Feign 接口 + domain + fallback factory：

| 接口 | 服务 | 说明 |
|------|------|------|
| `RemoteUserService` | system | 后台用户查询/注册 |
| `RemoteLogService` | system | 登录/操作日志 |
| `RemoteFileService` | file | 文件上传 |
| `RemoteCategoryService` / `RemoteBrandService` / `RemoteProductService` | product | 分类/品牌/商品 |
| `RemoteUserInfoService` / `RemoteUserAddressService` | user | 会员/地址 |
| `RemoteCartService` | cart | 购物车选中列表等 |
| `RemoteOrderInfoService` | order | 按订单号查订单 |

### 5.11 spzx-common（公共模块）

## 六、核心业务流程源码级解析

### 6.1 后台登录 `/login`（auth → system → Redis）

源码路径：`spzx-auth` → `SysLoginService.login()` → `TokenService.createToken()`

```
1. 网关 ValidateCodeFilter 校验验证码（Redis 比对）
2. SysLoginService.login(username, password)
   ├─ 校验参数非空、长度
   ├─ 查黑名单 IP（Redis: sys_config:sys.login.blackIPList）
   ├─ Feign RemoteUserService.getUserInfo() → spzx-system 查 sys_user + 角色/权限
   ├─ SysPasswordService.validate()：BCrypt 比对 + 错误次数限制（5 次锁 10 分钟）
   ├─ Feign RemoteLogService.saveLogininfor() 记登录日志
   └─ 返回 LoginUser
3. TokenService.createToken(loginUser)
   ├─ 生成 token（UUID）
   ├─ Redis 存会话：login_tokens:{token} → LoginUser，TTL 720 分钟
   └─ JWT 签名：{user_key, user_id, username}（JWT 只做"凭证"，状态在 Redis）
```

### 6.2 请求鉴权（网关 AuthFilter）

```
1. 白名单匹配（security.ignore.whites）→ 通过则直接放行
2. 取 Authorization 头，去掉 "Bearer " 前缀
3. JwtUtils.parseToken() 解析出 {user_id, user_key, username}
4. 查 Redis login_tokens:{user_key} 是否存在 → 不存在返回 401
5. 注入请求头 x-user-id / x-username / x-user-key，移除 from-source
6. 下游服务 HeaderInterceptor 把请求头塞进 SecurityContextHolder（ThreadLocal）
7. 剩余 TTL < 2h 时自动续期（总 12h）
```

### 6.3 下单主流程（order 服务）⭐面试重点

源码路径：`spzx-order` → `OrderInfoServiceImpl.submitOrder()`

```
1. 防重复提交：Lua 脚本原子 "GET user:tradeNo:{userId} == tradeNo ? DEL : 0"
2. 校验订单项非空
3. 价格校验：Feign 批量查最新价，与提交价比对，变化则提示并刷新购物车价格
4. 库存锁定：Feign RemoteProductService.checkAndLock(orderNo, skuList)
   → product 服务内：
     a. Redis setnx "sku:checkAndLock:{orderNo}" 防 Feign 重试（1h 有效）
     b. 逐 SKU 检查库存（for update 行锁）
     c. 库存够 → 逐 SKU 执行锁定 SQL（available-lock，lock+）
     d. 锁定明细存 Redis "sku:lock:data:{orderNo}"
5. 保存订单：order_info + order_item + order_log（事务）
   → 异常则发 MQ 消息解锁库存
6. 删除购物车选中商品（Feign）
7. 发延迟消息：15 分钟后（演示 1 分钟）自动关单 → 消费者关单 + 解锁库存
```

### 6.4 支付流程（payment → MQ → order → MQ → product）

```
用户点支付
  → /payment/alipay/submitAlipay/{orderNo}
  → 保存 payment_info（Feign 查订单）
  → 返回支付宝 WAP 支付表单（H5 跳转支付宝）
支付宝扣款成功
  → 异步回调 /payment/alipay/callback/notify
  → AlipaySignature.rsaCheckV1 验签
  → 更新 payment_info 状态（TRADE_SUCCESS）
  → 发 MQ：spzx.payment → spzx.payment.pay → 订单号
订单服务监听
  → processPaySucess：order_status 0 → 1，记录支付时间
  → 发 MQ：spzx.product → spzx.minus → 订单号
商品服务监听
  → minus(orderNo)：setnx 去重 → 按锁定明细扣减库存 → 删除锁定缓存
```

### 6.5 库存模型（product 服务）

`sku_stock` 表四字段：

| 字段 | 含义 | 关系 |
|------|------|------|
| total_num | 总库存 | = available + lock + sale |
| lock_num | 锁定库存（下单未支付） | 下单 +，支付/取消 - |
| available_num | 可用库存 | 下单 -，解锁/取消 + |
| sale_num | 已售 | 支付 + |

三个关键 SQL（`SkuStockMapper.xml`）：
- `check`：`SELECT ... FOR UPDATE`（行锁）
- `lock`：`available_num = available_num - n, lock_num = lock_num + n WHERE available_num >= n`
- `minus`：`lock_num = lock_num - n, sale_num = sale_num + n`
- `unlock`：`available_num = available_num + n, lock_num = lock_num - n`

## 七、关键技术点详解

### 7.1 缓存三兄弟（ProductServiceImpl 是最好的教材）

- **穿透**（查不存在的数据）：`ItemServiceImpl` 用 **Redis Bitmap**（`sku:product:data`，bit=1 表示 SKU 存在），查不到直接拒绝；`getProductSku` 连 null 也缓存（短 TTL）
- **击穿**（热点 key 过期）：`getProductSku` 用 `setIfAbsent` 分布式锁，抢锁失败自旋重试；释放锁用 **Lua 保证原子性**（只释放自己的锁）
- **雪崩**（大量 key 同时过期）：过期时间 = 基础值 + `Random(0~5)` 分钟
- **一致性**：`updateProduct` 用**延时双删**（先删缓存 → 更新 DB → 睡 500ms → 再删缓存），配合 Redis 里的短 TTL 兜底

### 7.2 分布式锁 / 幂等标记（注意区分两者）

| 场景 | 标记 key | 用途 |
|------|----------|------|
| 缓存重建锁 | `product:sku:lock:{skuId}`（5s） | 防止缓存击穿，多个线程抢一个锁 |
| Feign 重试去重 | `sku:checkAndLock:{orderNo}`（1h） | 防止库存被重复锁定 |
| 消息消费去重 | `sku:unlock:{orderNo}` / `sku:minus:{orderNo}`（1h） | MQ 重投不重复处理 |
| 下单防重 | `user:tradeNo:{userId}`（5min）+ Lua | 防止表单重复提交 |

共同点：全部用 `setIfAbsent`（SETNX）+ 过期时间 + 必要时 Lua 原子释放。**局限**：锁过期后业务未完成会出问题 → 学习 Redisson 看门狗机制。

### 7.3 消息可靠性（RabbitMQ）

- 生产端：`publisher-confirm-type: CORRELATED` + `publisher-returns: true`（见 Nacos 配置）
- 消费端：`acknowledge-mode: manual` 手动 ack，业务成功才 `basicAck`
- 幂等：消费前 `setnx` 去重标记
- 延迟消息：`spzx.cancel.order` 交换机 → 消息 TTL 1 分钟 → 无人消费进入死信队列 → 死信消费者关单

### 7.4 BFF 聚合（channel 服务）

`ItemServiceImpl.item()` 用 `CompletableFuture` 编排 6 个 Feign 调用：
```
productSku（先取 SKU，拿到 productId）
 ├─ thenAccept → product（商品信息）
 ├─ thenAccept → productDetails（详情图）
 ├─ thenAccept → skuSpecValue（规格映射）
 └─ thenAccept → skuStock（库存）
runAsync → skuPrice（最新价格）
allOf(...).join() 阻塞等待全部完成
```
配套 `ThreadPoolConfig` 自定义线程池（核心/最大线程数、队列、拒绝策略），避免用公共 ForkJoinPool。

### 7.5 双端认证 + 内部调用安全

- 后台登录走 `spzx-system` 的 `sys_user`；H5 走 `spzx-user` 的 `user_info`
- 服务间暴露的接口一律 `@InnerAuth`：切面校验 `from-source: inner` 请求头
- 网关对外请求**强制移除** `from-source` 头 → 外部无法伪造内部调用

## 十、常见问题 FAQ

**Q1：为什么 JWT 校验放网关而不是各服务？**
统一入口做一次鉴权，下游服务无需重复解析；同时集中管理白名单、验证码、XSS 等横切逻辑。

**Q2：JWT 本身不可撤销，怎么实现"退出登录立即失效"？**
JWT 只携带用户标识，真正的会话在 Redis（`login_tokens:{token}`）。退出时删 Redis 即可，网关校验 Redis 存在性，所以"不可撤销"问题被绕过了。

**Q3：Feign 调用为什么都带 `@RequestHeader(FROM_SOURCE)`？**
服务间调用必须带 `from-source: inner` 头才能通过 `@InnerAuth` 校验；该头在网关入口被强制移除，防止外部伪造。

**Q4：为什么下单选中的购物车商品在 Redis 而不在 MySQL？**
购物车是高频、低一致性的数据，Redis Hash 天然适合；订单系统通过 `@InnerAuth` 接口一次性取走选中项。

**Q5：库存锁定失败怎么办？**
`checkAndLock` 返回非空错误串 → 订单服务抛异常终止下单；Feign 重试被 Redis setnx 标记拦截（1h 内不重复锁定）；订单保存失败/超时未支付都会发 `unlock` 消息解锁库存。

**Q6：消息重复消费怎么处理？**
消费者用 `setnx "sku:unlock:{orderNo}"` 做幂等标记，重复消息直接跳过；配合手动 ack，业务成功才确认。

**Q7：延迟关单为什么用 RabbitMQ 死信队列？**
RabbitMQ 原生不支持定时消息。方案：消息发到 `spzx.cancel.order` 交换机，队列设 TTL=1 分钟且无消费者 → 到期进入死信队列 → 死信消费者执行关单。

**Q8：`@InnerAuth(isUser=true)` 和 `@InnerAuth` 区别？**
默认 `@InnerAuth` 只校验 `from-source: inner`；`isUser=true` 时额外从请求头解析用户信息放入 SecurityContext（看 CartController 中被注释的示例）。

**Q9：启动报 Nacos 连接失败？**
检查 `pom.xml` 的 `nacos.addr` 是否可达（`telnet 地址 8848`），并确认 Nacos 控制台已导入 `doc/nacos_config_export_*.zip`。

**Q10：从哪里看接口文档？**
服务启动后访问 `http://localhost:端口/doc.html`（Knife4j），网关聚合文档在 `http://localhost:8080/v3/api-docs`。
